# Генератор карти — вимоги

Похідне від `00-opys-gry.md`, `03-karta.md`, `04-dynamika.md`. POC-етап 0a.

Позначки: **[ЗАФІКСОВАНО]** — рішення прийняте; **[ПРОПОЗИЦІЯ]** — моя
рекомендація, ще не підтверджена.

## Мета

Інструмент, що будує лабіринт заданого розміру з гарантованою мінімальною
довжиною шляху, розставляє ігрові сутності й віддає дані карти у форматі
для `Game.registerMap`. Прибирає ручне малювання карт і дає багато рівнів
пізніше.

## Принцип: генератор незалежний від ядра [ЗАФІКСОВАНО]

- **Ядро** знає тільки `passable[y][x]` — прохідна клітинка чи ні, плюс
  старт/фініш. Більше нічого.
- **Генератор** видає два шари: *логічний* (прохідність — для ядра) і
  *шар картинок* (готові id плиток — для рендера).
- **Рендер** теж знає рівно одне: `tiles[y][x]` → картинка з реєстру.
  Ні прохідність, ні терен, ні автотайлінг його не стосуються.
- Наслідок: усе багатство карти (гори, ліси, водойми, чудеса світу,
  автотайлінг) масштабується **всередині генератора**; ядро, динаміка й
  рендер не змінюються ніколи.

## Непрохідна зона — це ціла клітинка, не грані [ЗАФІКСОВАНО]

- Кожна клітинка або прохідна, або ні. Стіни займають місце на сітці — як
  гори/ліс у «Героях 3». **Не** тонкі стіни на межах клітинок.
- Причини: квадратний PNG-тайл лягає 1:1 на клітинку; колізія тривіальна
  (`passable[y][x]`); гори, ліс, ріка, лава, провалля — це area-перешкоди,
  а не лінії; одна модель на все.
- **Паркан / двері** моделюємо як лінію клітинок-стін з однією клітинкою-
  «дверима» (перешкода із завданням). Окремого типу «грань» не заводимо.
- Наслідок: стіни з'їдають ~половину сітки, тому для шляху ≥ 25 сітка
  має бути помітно більшою — для POC 24 × 18 (з `03-karta.md`).

## Два проходи генерації [ЗАФІКСОВАНО]

Генерація ділиться на два незалежні проходи:

1. **Прохід 1 — світ.** Створює лабіринт і його вигляд: прохідність,
   старт/фініш, терен, великі об'єкти. Про ігрові сутності не знає нічого.
2. **Прохід 2 — розстановка.** Бере готовий світ і розставляє **перешкоди,
   скрині, помічників** за правилами балансу.

Навіщо так:
- проходи можна писати й міняти окремо;
- на етапі 0a потрібен **лише прохід 1** (порожній лабіринт);
- один і той самий світ можна переграти з іншою складністю — просто
  перезапустивши прохід 2 з іншими параметрами.

---

# Прохід 1 — світ

## Параметри

| Параметр | Опис | POC |
|---|---|---|
| `seed` | ціле число; той самий seed + параметри → та сама карта | будь-яке |
| `width`, `height` | розмір сітки в клітинках | 24 × 18 |
| `minPathLength` | мін. довжина найкоротшого шляху старт → фініш (BFS) | 25 |
| `braiding` | 0..1: частка тупиків, які «розшиваємо» в петлі (0 = ідеальний лабіринт, максимум тупиків) | 0.3–0.5 |
| `corridorWidth` | ширина проходів у клітинках | 1 |
| `alcoves` | 0..1: частка придатних стін, що стають нішами збоку | 0.35 |
| `clearings` | скільки галявин 2×2 прорізати | 3 |
| `terrainScale` | скільки клітинок припадає на одну зону ландшафту | 40 |
| `forest`, `mountain`, `water` | ваги при роздачі теренів зонам | 0.45 / 0.35 / 0.2 |
| `border` | суцільна стіна по периметру | так |

Старт і фініш — по 2 сусідні прохідні клітинки. Позиції задає генератор,
**по відстанях у лабіринті, а не по кутах сітки** (див. «Де ставимо старт
і фініш»).

## Гарантії

1. **Повна зв'язність**: з будь-якої прохідної клітинки досяжна будь-яка
   інша (жодних ізольованих кишень). Тупики — так, ізольовані зони — ні.
2. **Довжина шляху**: найкоротший шлях старт → фініш ≥ `minPathLength`.
3. **Старт і фініш**: існують, прохідні, рознесені, мають місце під
   2 клітинки кожен.
4. **Периметр** — суцільна стіна.
5. **Детермінізм**: однаковий вхід → однакова карта.
6. **Розмір** ≥ видимої сітки 11 × 9 (інакше камері немає куди рухатись).

Якщо гарантію не вдалось виконати (напр. шлях закороткий) — генератор
детерміновано пробує `seed+1`, `seed+2`, … і повертає фактичний
`usedSeed` у метаданих.

## Алгоритм [ЗАФІКСОВАНО]

1. Робоча сітка: проходи на непарних координатах, стіни між ними на парних.
2. **Рандомізований DFS** (recursive backtracker) — «прокопуємо» ідеальний
   лабіринт (одна доріжка між будь-якими точками).
3. **Braiding**: обходимо тупики, з імовірністю `braiding` прибираємо одну
   стіну тупика → з'являються петлі, менше глухих кутів.
4. Ставимо старт і фініш (по 2 клітинки) — див. нижче.
5. **BFS**: міряємо найкоротший шлях. Закоротко → регенеруємо із `seed+1`.
6. **BFS-заливка**: перевіряємо повну зв'язність. Ізольовані зони →
   регенеруємо або заливаємо стіною.

## Де ставимо старт і фініш [ЗАФІКСОВАНО]

**Проблема.** Перша версія брала кути сітки: старт — найближча пара до
лівого верхнього кута, фініш — до правого нижнього. Напрямок руху був
відомий ще до першого ходу: іди по діагоналі вниз-праворуч. Карта
різна, задача та сама.

**Рішення.** Обидві точки шукаємо по відстанях у самому лабіринті:

1. З **випадкової** прохідної клітинки BFS → найдальша від неї. Це кінець
   «діаметра» лабіринту: закуток на околиці, але з якого боку карти —
   вирішує seed. Це **старт**.
2. BFS зі старту → **фініш беремо випадково** серед клітинок, не ближчих
   за поріг. Саме випадково: «найдальша від старту» так само однозначна,
   як і кут, тільки рахувати складніше.
3. Поріг = максимум із `minPathLength` (гарантія 2) і 80 % діаметра
   лабіринту — щоб фініш не сідав десь посеред дороги.
4. Друга клітинка пари — сусідня прохідна. Для фінішу беремо ту, що далі
   від старту: обидві клітинки фінішу мають бути «у фініші», а не одна з
   них за крок назад по дорозі.

Випадковість тут іде з окремого потоку (`usedSeed ^ 0x2545f491`), щоб
зміни в копанні лабіринту не зсували вибір точок і навпаки. Детермінізм
не страждає: той самий seed → ті самі точки.

**Наслідок.** Напрямок «старт → фініш» рівномірно розкидано по всіх
чотирьох чвертях (300 seed-ів, 24 × 18: 66-89 випадків на чверть проти
300 з 300 в одну до правки). Фініш може виявитись і недалеко по прямій —
але 80 кроків по лабіринту; це нормально, дорогу однаково треба шукати.
Довжина шляху при цьому теж зросла: медіана 61 клітинка проти 44 на тих
самих 300 seed-ах.

## Місце збоку від дороги [ЗАФІКСОВАНО]

**Проблема.** У лабіринті шириною 1 немає поняття «збоку». Скриня чи
помічник у коридорі, який гравець мусить пройти, перестає бути
необов'язковим — а за `00-opys-gry.md` скрині й помічники **ніколи не
блокують шлях**. Отже, місце «поруч із дорогою» має створювати вже
крок 1, інакше проходу 2 нема куди класти предмети.

Два інструменти, обидва вмикаються параметром і обидва можна вимкнути в нуль:

### Ніші (`alcoves`)

Клітинка-стіна, у якої **рівно один** прохідний сусід, стає прохідною.
Умова «рівно один» — не деталь реалізації, а гарантія: ніша лишається
тупиком, не з'єднує два коридори, не робить петлю і тому **ніколи не
лежить на шляху**. Захід коштує рівно 2 кроки (туди й назад) — приємне
маленьке рішення для дитини при бюджеті 5 кроків на хід.

Умова перевіряється **повторно перед кожним прорізанням**: сусідня ніша
могла змінити картину.

### Галявини (`clearings`)

Блок 2×2 робиться прохідним цілком, якщо в ньому вже є хоча б одна
прохідна клітинка (тоді галявина гарантовано приєднана) і не всі чотири
(інакше нічого не міняється). Дає простір, у якому предмет стоїть збоку,
а не поперек дороги, і розбиває монотонність коридорів.

Галявини створюють петлі — це навмисно: саме петлі роблять сусідні
клітинки обхідними.

### Скільки це дає (seed 12345, 24 × 18)

| Налаштування | Прохідних клітинок | З них можна обійти | Шлях |
|---|---|---|---|
| ніші 0, галявини 0 | 176 | 18 (10%) | 59 |
| тільки ніші 0.35 | 189 | 28 (15%) | 59 |
| тільки галявини 3 | 183 | 69 (38%) | 55 |
| **разом 0.35 / 3 (типово)** | **195** | **49 (25%)** | **59** |
| щедро 0.6 / 5 | 205 | 95 (46%) | 58 |

«Можна обійти» = клітинка не є вузьким місцем (articulation point), тобто
її видалення не роз'єднує карту. Це і є множина, з якої прохід 2 бере
місця під скрині й помічників.

Галявини дають більший приріст, ніж ніші, бо створюють петлі; ніші дають
дешеві тупики, які не чіпають довжину шляху. Типові значення — компроміс:
чверть карти придатна під предмети, а лабіринт лишається лабіринтом.

### Чого не робимо

**Не розширюємо коридори до 2 клітинок** (`corridorWidth` лишається 1).
На 24 × 18 сітка лабіринту всього 11 × 8 клітинок — подвоєння ширини
з'їло б її майже повністю, і лабіринт перестав би бути лабіринтом. Ніші
й галявини дають той самий ефект («є куди ступити вбік») локально й за
частку місця. До ширших проходів можна повернутись на більших картах.

## Візуальний шар — як генерувати картинку

**Генератор видає опис картинки, не пікселі** [ЗАФІКСОВАНО]. Плоский PNG
усієї карти — хіба як опційний прев'ю-thumbnail, не робочий шлях (немає
куллінгу, не анімується).

## Резолв картинок — на генерації, не на рендері [ЗАФІКСОВАНО]

Найважливіше рішення контракту.

**Рендер нічого не знає про терен, автотайлінг і логіку світу.** Він читає
готову сітку **id картинок** і малює. Уся семантика (де гори, де ліс, який
краєвий тайл) живе в генераторі й «випікається» в id на етапі, який ми
називаємо *резолв* — умовна компіляція карти.

```
                 ГЕНЕРАТОР (час розробки)                    ГРА (рантайм)
  ┌────────────┐   ┌──────────┐   ┌──────────────┐        ┌──────┐
  │ 1. топологія│──▶│2. терен  │──▶│3. резолв     │──▶ дані ├──────┤
  │  лабіринт   │   │ гори/ліс/│   │  терен → id  │   карти │ ядро │ passable
  │  старт/фініш│   │ вода/    │   │  картинок    │        │рендер│ tiles → картинка
  └────────────┘   │ містки   │   └──────────────┘        └──────┘
        │          └──────────┘          │
        ▼                                ▼
   passable[y][x]              tiles[y][x] = 'grass-edge-ne'
   (їде в дані)                       (їде в дані)
                    terrain — проміжний, рендер його не читає
```

### Чому так [ЗАФІКСОВАНО]

- **Рендер лишається тупим і назавжди готовим.** Він уміє рівно одне:
  `tiles[y][x]` → картинка з реєстру. Ускладнення генератора (автотайлінг,
  біоми, переходи між теренами) **не торкаються рендера взагалі**.
- **Логіку генерації можна міняти будь-як** — контракт з рендером не рухається.
- **Дорога робота робиться один раз**, а не 60 разів на секунду в грі.
- **Карта — артефакт компіляції, а не джерело.** Тому запікати id картинок
  безпечно: змінився тайлсет → перезапустили резолв, а не правимо карти руками.

### Умова, за якої це безпечно [ЗАФІКСОВАНО]

Карту треба **вміти відтворити**. Тому `meta` зберігає все, з чого вона
зроблена: `seed`, `usedSeed`, усі параметри, версію генератора й версію
резолвера. Той самий вхід → той самий світ, тож перерезолвити карту під
новий тайлсет = перезапустити генератор із записаного `meta` й новим
резолвером.

`terrain` у файл карти **не потрапляє**. Він живе тільки всередині
генератора. Гра про терен не знає взагалі — ні ядро, ні рендер.

## Контракт кроку 1 — об'єкт `world` [ЗАФІКСОВАНО]

Це **внутрішній** контракт генератора: те, що крок 1 віддає, крок 2
доповнює, а крок 3 (резолвер) читає. У гру він не потрапляє — у гру йде
результат серіалізації (див. «Контракт шару 1»).

### Поля

| Поле | Тип | Пише | Читає |
|---|---|---|---|
| `size` | `{ w, h }` | крок 1 | усі |
| `passable` | `boolean[][]` | крок 1 | кроки 2, 3, серіалізація |
| `start` | `[{x,y},{x,y}]` | крок 1 | кроки 2, 3, серіалізація |
| `finish` | `[{x,y},{x,y}]` | крок 1 | кроки 2, 3, серіалізація |
| `path` | `{x,y}[]` | крок 1 (BFS) | крок 2, в'юер, шар 2 |
| `terrain` | `string[][]` | крок 2 | крок 3 (назовні не йде) |
| `props` | `{id,x,y}[]` | крок 2 | крок 3, серіалізація |
| `meta` | object | усі кроки | серіалізація |

`passable` — булеві; у файл карти вони їдуть як є, без перетворення.
`terrain` — двовимірний масив id (`[['grass','forest',…],…]`), як і `tiles`.
Символьних легенд не заводимо ніде.

`path` (найкоротший шлях старт → фініш) крок 1 і так рахує через BFS, тому
віддає безкоштовно. Він потрібен кроку 2 (де класти містки й красиве —
там, де гравець точно пройде) і проходу 2 (розкидати скрині вздовж шляху).

### Помічники (не серіалізуються)

```js
world.at(x, y)        // → { inside, passable, terrain }
world.isPassable(x,y) // → boolean; за межами карти завжди false
world.hash(x, y)      // → ціле ≥ 0, детерміноване від usedSeed і координат
world.rng()           // → 0..1, послідовний seeded-генератор
```

- **`at(x, y)` за межами карти не падає**, а повертає
  `{ inside: false, passable: false, terrain: world.outsideTerrain }`
  (за замовчуванням `'mountain'`). Це навмисно: автотайлінг на краю карти
  тоді не потребує жодного спецкейсу — зовнішній світ просто «ще гори».
- **`hash(x, y)` проти `rng()`** — різні інструменти, плутати не можна:
  `hash` залежить від координат і не залежить від порядку викликів
  (тому годиться для вибору варіанту плитки в резолвері, який може
  бігти по клітинках у будь-якому порядку); `rng()` — послідовний, для
  рішень кроку 2 (скільки озер, де саме), і порядок викликів має значення.

### Конвеєр

```js
const world = MapGen.carveMaze(params);      // крок 1 → world
MapGen.scatterTerrain(world);                // крок 2 → доповнює world
const tiles = MapGen.resolveTiles(world, 'autotile'); // крок 3 → tiles
const data  = MapGen.toMapData(world, tiles);         // → Game.registerMap(...)
```

Кожен крок можна викликати окремо — це і є та гнучкість, заради якої
резолв винесено з рендера.

### На етапі 0a

Крок 2 розкидає терен (див. нижче), крок 3 резолвить картинки
автотайлінгом. `props` поки не заповнюється — це прохід 2.

## Резолвер — замінна стратегія [ЗАФІКСОВАНО]

Крок 3 винесений в окремий модуль, який можна підмінити. Контракт:

```js
// найпростіша можлива стратегія — для ілюстрації контракту
MapGen.registerResolver({
  id: 'example',
  name: 'Дві плитки (прохідно / ні)',
  resolve(world, x, y) {
    return world.passable[y][x] ? 'grass-0' : 'forest-0';
  },
});
```

- `world` дає резолверу все: `passable`, `terrain`, `size`, `at(x, y)`
  (безпечне читання сусідів за межами карти), `hash(x, y)` (детермінований
  шум від seed — для вибору серед взаємозамінних варіантів).
- Повертає **id картинки** з реєстру плиток.
- Резолвер викликається для кожної клітинки; результат лягає в `tiles`.

### Дорожня карта резолверів

| Резолвер | Що робить | Коли |
|---|---|---|
| `autotile` | терен + 8 сусідів (з діагоналями) → 47 варіантів на терен; трава — 3 взаємозамінні | **зараз**, єдиний |
| `props` | оверлеї на кілька клітинок (чудеса світу) | коли буде арт |

Сходинку «плоский колір → тайлсет з автотайлінгом» уже пройдено, і вона
коштувала рівно один новий файл резолвера: **ні рендер, ні контракт, ні
ядро не змінились**. Рівно заради цього резолв і винесли на генерацію.

В проєкті тримаємо **один** резолвер і один набір плиток [ЗАФІКСОВАНО].
Проміжні (дві плитки, набір на 16) прибрано, щоб не тримати зайвого.
Механізм реєстрації лишається — новий резолвер можна додати, коли буде
причина.

Процедурний SVG як джерело картинок не розглядаємо [ЗАФІКСОВАНО]: SVG уже
показав себе негарним (див. історію вибору стилю персонажів), а чудеса
світу процедурно не намалюєш впізнавано.

## В'юер замість читання даних [ЗАФІКСОВАНО]

Карту оцінюємо **очима в браузері**, а не читанням масивів. Тому
`tools/map-generator.html` — це і генератор, і в'юер: seed + параметри +
вибір резолвера → згенерувати → одразу побачити карту цілком.

Наслідок для формату даних: **читабельність даних людиною більше не є
вимогою**. Тому `tiles` — це чесний двовимірний масив id (`[['grass-0',
…], …]`), без символьних легенд. Для 24 × 18 це ~7 КБ — байдуже.

В'юер малює тим самим кодом і тим самим реєстром плиток, що й гра
(WYSIWYG). Додатково показує дебаг-оверлеї: прохідність, найкоротший шлях,
старт/фініш, номери клітинок.

### Типи терену [ЗАФІКСОВАНО]

Терен — **внутрішня річ генератора** (крок 2), у гру не потрапляє. Тому
розширювати його дешево.

| id | Прохідний | Роль |
|---|---|---|
| `grass` | так | усе, де можна ходити |
| `forest` | ні | ліс |
| `mountain` | ні | гори |
| `water` | ні | вода |

Прохідність вирішена ще на кроці 1; крок 2 лише розфарбовує те, що вже
непрохідне. Терен **не може** зробити клітинку прохідною чи ні — інакше
крок 2 ламав би гарантії кроку 1 (зв'язність, довжину шляху).

**Як розкидаємо.** Кидаємо по карті `w × h / terrainScale` центрів зон
(на 24 × 18 це ~11). Терени роздаємо зонам за вагами — не кидаємо кубик
кожній зоні окремо: на десятку зон незалежний розіграш легко дає карту
зовсім без води. Далі кожна непрохідна клітинка бере терен найближчого
центру. Виходять суцільні масиви, а не сіль-перець.

Дві дрібниці роблять межі живими:

- відстань до центру трохи зашумлена — щоб зони не різались по лінійці;
  шум береться від **позиції** (`world.hash(x, y)`), а не від порядку
  обходу, тож той самий seed дає ті самі межі;
- один прохід згладжування: клітинка, у якої 3-4 непрохідні сусіди одного
  чужого терену, переходить до них. Прибирає поодинокі крапки, які лишає
  шум.

Ваги — це частка **зон**, а не площі. Площа виходить інша, бо зона фарбує
тільки ті клітинки, де стоїть стіна, а стіни лежать нерівномірно. На
шести seed-ах 24 × 18: ліс 38-59 %, гори 23-41 %, вода 17-27 %.

### Автотайлінг [ЗАФІКСОВАНО]

Резолвер `autotile` для кожної непрохідної клітинки збирає 8-бітну маску —
чи такий самий терен на 4 сторонах і 4 діагоналях, за годинниковою стрілкою
від півночі: 1 = Пн, 2 = ПнСх, 4 = Сх, 8 = ПдСх, 16 = Пд, 32 = ПдЗх,
64 = Зх, 128 = ПнЗх. id виду `forest-213`.

- Біт стоїть → з того боку масив продовжується, край не малюємо.
- Біт не стоїть → малюємо край; де два краї сходяться, кут заокруглено.
- **За межами карти вважаємо, що терен той самий.** Тому масив на краю
  екрана йде «за кадр», а не обривається рамкою, і жодного окремого коду
  для країв не треба.

Ключове правило: **діагональ рахується, тільки якщо стоять обидві сусідні
сторони.** Інакше форму кута однаково визначають сторони, і діагональ
нічого не додала б. Саме тому з 256 комбінацій лишається 47 різних форм,
а не 256 картинок.

Чому з діагоналями, а не простіший набір на 16 (тільки сторони): без
діагоналей внутрішні (увігнуті) кути масиву гострі, а два масиви, що
торкаються по діагоналі, лишаються розірваними — і артом це не лікується,
бо потрібної картинки в наборі просто немає. Перевірено чисельно: на 47
найдовший розрив по шву — 0.25 px, на 16 — 11.75 px. Набір на 16 спробували
й прибрали.

Трава — три взаємозамінні варіанти, вибір через `world.hash(x, y)`; це
лише щоб поле не рябіло сіткою.

**Вимоги до самих картинок — окремим файлом:** `06-specyfikaciya-tayliv.md`
(які файли, як звуться, правила стиковки, промти для AI). Це технічне
завдання на арт: перегенерував за ним усі файли — і стиль карти інший, а код
не змінився.

**Арт поки програмний** — 144 плитки (3 трави + 3 × 47): рівний колір,
крони, гребені вершин, брижі, піщаний берег. Скрипт, що їх малює, живе
**поза грою** (`~/Projects/maxmap-tilegen/gen-tiles.py`): гра бачить тільки
готові PNG. Коли з'явиться справжній арт, PNG просто заміняються, id ті
самі, код не міняється.

### Багатоклітинкові об'єкти [ЗАФІКСОВАНО]

- На карті можуть бути великі об'єкти більші за клітинку: Еверест,
  Мачу-Пікчу та інші чудеса світу (ідея з Civilization V) — це ще й
  повчально.
- Реалізація: `props` — список `{ id, x, y }`; розмір `w × h` береться з
  реєстру. Рендер малює ілюстрацію на прямокутнику w×h клітинок поверх
  плиток.
- Генератор позначає слід (footprint) об'єкта як **непрохідний** у
  логічному шарі.
- Ядро й динаміка **не змінюються** — вони бачать лише прохідність.
- Освітні факти-попапи про чудо («Мачу-Пікчу — місто інків у Перу») —
  пізніший ігровий шар, не відповідальність генератора.

# Прохід 2 — розстановка сутностей

Не потрібен на етапі 0a; потрібен від етапу 1. Правила виводимо з
`00-opys-gry.md`.

## Що розставляє

- **Перешкоди** (гейт: блокують шлях, поки не виконано завдання) —
  мінімум **3 на рівень**.
- **Скрині** — багато, малоцінні.
- **Помічники** — мало.

## Правила [ПРОПОЗИЦІЯ]

- **Перешкоди — тільки у «вузьких місцях»**: на клітинках, без яких
  старт і фініш роз'єднуються (articulation points). Тоді перешкода
  справді гейтить прогрес, а не обходиться збоку.
- **Скрині й помічники — ніколи у вузьких місцях**: тільки на клітинках,
  які можна обійти (з `00-opys-gry.md`: «клітинки зі скринями/помічниками
  не блокують шлях»). Природні місця — **ніші й галявини**, які крок 1
  спеціально для цього й створює, плюс тупики та бічні відгалуження.
- **Розподіл**: не збивати в купу, розкидати вздовж шляху.
- **Помічники — на розвилках**, де підказка напрямку справді цінна.

## Взаємодія з ядром

Перешкода = клітинка **непрохідна, поки завдання не виконане**; після
виконання стає прохідною. Тобто ігровий шар просто перемикає прохідність
клітинки — ядро й далі знає лише `passable`.

# Контракт шару 1 — статичний всесвіт [ЗАФІКСОВАНО]

Версія контракту: **1**. Це **єдине**, що генератор віддає назовні.

## Два споживачі, і більше жодного

| Споживач | Питання, на яке відповідають дані | Поля |
|---|---|---|
| **ядро** | куди можна ходити, звідки почали, де кінець | `passable`, `start`, `finish` |
| **рендер** | що намалювати в цій клітинці | `tiles`, `props` |

Як генератор побудував карту — лабіринт, терен, автотайлінг — **назовні не
видно**. Ці поняття у файлі карти не згадуються.

Шар 2 (скрині, помічники, перешкоди, завдання) — пізніше, окремим полем
`entities`. Шар 1 при цьому не змінюється.

## Домовленості

- `x` — колонка (0 = зліва), `y` — рядок (0 = зверху). Доступ: `[y][x]`.
- Файл `src/maps/<id>.js` містить **лише дані**: один виклик
  `Game.registerMap({...})`.

## Контракт

```js
Game.registerMap({

  // ─── ІДЕНТИФІКАЦІЯ ────────────────────────────────────────────────
  id: 'poc-01',            // унікальний id рівня; ним карта обирається в грі
  version: 1,              // версія цього контракту
  size: { w: 12, h: 8 },   // розмір сітки в клітинках

  // ─── ДЛЯ ЯДРА: куди можна ходити ──────────────────────────────────
  // true — по клітинці можна ходити, false — не можна.
  // Рядків рівно size.h, у кожному рівно size.w значень.
  // Така сама форма, як у tiles: [y][x].
  passable: [
    [false, false, false, false, false, false, false, false, false, false, false, false],
    [false, true,  true,  true,  true,  true,  true,  true,  true,  true,  true,  false],
    [false, true,  false, false, false, false, true,  false, false, false, true,  false],
    // ... решта рядків так само
  ],

  // дві сусідні клітинки старту: [0] — герой 1 (дитина), [1] — герой 2.
  // Обидві гарантовано прохідні.
  start: [ { x: 1, y: 1 }, { x: 2, y: 1 } ],

  // дві сусідні клітинки фінішу. Рівень пройдено, коли обидва герої стоять
  // на цих клітинках. Обидві гарантовано прохідні.
  finish: [ { x: 9, y: 6 }, { x: 10, y: 6 } ],

  // ─── ДЛЯ РЕНДЕРА: що малювати ─────────────────────────────────────
  // id картинки на кожну клітинку. Рендер бере картинку з реєстру плиток
  // і малює. Жодної логіки: ні сусідів, ні терену, ні прохідності.
  // Форма масиву — така сама, як у passable: size.h рядків по size.w штук.
  tiles: [
    ['forest-28', 'forest-124', 'forest-124', 'forest-112', 'mountain-0', /* … */ ],
    ['forest-31', 'grass-2',    'grass-0',    'grass-1',    'grass-0',    /* … */ ],
    // ... решта рядків так само
  ],

  // великі ілюстрації поверх плиток (Еверест, Мачу-Пікчу).
  // Розмір w×h береться з реєстру об'єктів, тут лише де саме поставити.
  // У першій версії завжди порожній.
  props: [],

  // ─── СЛУЖБОВЕ: гра це не читає ────────────────────────────────────
  // усе, чим карту згенеровано — щоб її можна було відтворити або
  // перемалювати іншим набором картинок.
  meta: {
    seed: 12345,           // seed, який задали
    usedSeed: 12345,       // seed, який спрацював (міг зрости при ретраях)
    params: { width: 12, height: 8, minPathLength: 12, braiding: 0.4 },
    pathLength: 13,        // фактична довжина найкоротшого шляху старт → фініш
    generator: 'world-v1', // версія логіки генерації
    resolver: 'autotile',  // версія логіки вибору картинок
  },

});
```

## Реєстр плиток

Єдиний місток між id у `tiles` і картинкою. Рендер більше нічого не знає.

```js
// skin/skin.js — у циклі по теренах і 47 масках
Game.registerImage('grass-0',    'skin/grass-0.png');
Game.registerImage('forest-213', 'skin/forest-213.png');
```

Додати новий вигляд = новий рядок тут + новий PNG. Рендер не чіпаємо.

## Що з цим робить ядро

```js
Game.isPassable(map, x, y)   // → map.passable[y][x]
```

І все. Ядро не відкриває `tiles`, `props`, `meta`.

## Що з цим робить рендер

```js
drawCell(x, y, Game.images[map.tiles[y][x]]);
```

І все. Рендер не відкриває `passable`, `start`, `finish`, `meta`.

## Інваріанти (перевіряє `validateMap`)

1. `passable` — рівно `size.h` рядків, у кожному рівно `size.w` значень,
   тільки `true` / `false`.
2. `tiles` — рівно `size.h` рядків, у кожному рівно `size.w` id.
3. Периметр `passable` — суцільно `false`.
4. Кожен id у `tiles` є в реєстрі плиток; кожен id у `props` — у реєстрі
   об'єктів.
5. `start` — 2 сусідні прохідні клітинки; `finish` — теж; вони рознесені.
6. Усі прохідні клітинки взаємно досяжні (BFS-заливка, жодних ізольованих
   кишень).
7. Найкоротший шлях старт → фініш ≥ `meta.params.minPathLength`.
8. `meta` містить `usedSeed`, `params`, `generator`, `resolver` — інакше
   карту не відтворити.

# Формат виходу — шар 2 (розстановка)

Прохід 2 **не змінює** нічого з шару 1, а лише додає до того самого об'єкта:

  entities: {
    obstacles: [ { x, y, type: 'wall-door', task: 'math' } ],

шар накладає
поверх «зачинено, поки завдання не виконане».
